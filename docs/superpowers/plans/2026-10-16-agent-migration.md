# Agent 渐进迁移计划

**Goal:** 从自研单 Agent 逐步迁移到支持用户确认、恢复和专业 Agent 协作的 LangGraph 流程。

**Architecture:** 保留 Ollama SDK、MCP 工具和 MySQL 业务层；先接入单节点图，再拆分执行循环，随后接入持久化和用户确认，最后增加专业 Agent。LangChain 为可选集成，不作为前置要求。

**Tech Stack:** Python、LangGraph、Ollama SDK、FastMCP、MySQL、React。

**需求依据:** 本次聊天提出的用户判断、多 Agent 和从简到难迁移要求。“用户判断”暂按用户审批理解；账户体系作为条件性范围单列。

## 全局约束

- 本轮执行并验收阶段 1–3；阶段 4–8 留待后续实施。
- 每阶段独立验收后再推进；保留旧入口直到新旧行为通过回归。
- 检查点不保存 ClientSession、数据库连接等运行时对象；这些资源在每次执行时重新创建。
- 业务数据库和执行检查点职责分离；会话消息只能有一个权威来源。
- 当前 MCPToolRegistry 路径未调用 agent.policy.ToolPolicy；审批必须接入实际执行路径。
- 多用户发布前必须完成身份、计划权限和记忆隔离；客户端不能自行声明 confirmed 或 permissions。

## 5. 用户确认闭环（难）

修改 agent/graph.py、agent/policy.py、tooling/mcp.py、service/api/server.py、frontend/src/App.jsx；新增 tests/test_user_approval.py。

- [ ] 在真实工具执行前接通统一策略检查，先覆盖删除等高风险操作。
- [ ] 使用 interrupt 返回待审批工具、参数和变更摘要；在独立节点中暂停。
- [ ] 增加恢复接口，支持批准、拒绝；编辑参数作为后续小任务，编辑后重新验证和审批。
- [ ] 服务端绑定审批人、会话、调用参数与计划版本，拒绝伪造、重复和过期审批。
- [ ] 前端展示等待状态和结果；刷新后可恢复待审批界面。
- [ ] 暂停节点之前不产生需要重复执行的业务副作用；恢复后校验目标计划是否变化。

验收：未批准零写入；拒绝终止该操作；批准只执行一次；重启和重复点击均安全。

范围：service/api/server.py、service/storage/travel_db.py、service/agent/memory.py、service/agent/preference_profile.py 及相关工具。

- [ ] 若目标包含多个登录用户，先确定身份来源和可信服务端用户上下文。

## 7. 最小多 Agent（更难）

新增 agent/specialists.py、tests/test_multi_agent.py；修改 agent/graph.py。

- [ ] 先增加一个只读的行程审计 Agent，由协调者按需调用。
- [ ] 定义结构化结果：问题、证据、建议；专家只获得必要上下文和工具。
- [ ] 协调者统一回复和写入；设置总调用预算、超时和失败降级。
- [ ] 验证无委派循环、专家失败可退回单 Agent、工具权限不能提升。

验收：复杂行程检查比单 Agent 基线有可观察收益，调用次数和延迟可接受后再增加地点研究等角色。

## 8. 并行协作与迁移收尾（最高难度，按收益开展）

- [ ] 仅并行独立只读研究任务；共享计划由一个协调者提交修改。
- [ ] 定义结果合并、超时、冲突处理和版本校验；持久化写入不由多个专家竞争执行。
- [ ] 比较固定样例上的任务成功率、越权/误写、调用成本和延迟。
- [ ] 新入口稳定且回退验证通过后，删除旧循环和临时切换配置，更新 README。

验收：恢复、审批、并发和成本回归通过，再将新流程设为唯一默认入口。

## 延后项

不提前迁移整个 LangChain 模型/工具接口，不同时引入向量库、独立 Agent 微服务、消息队列或重写 HTTP 框架。出现具体需求后独立评估。

## 执行顺序

1 → 2 → 3 → 4 → 5 →（多用户上线前完成 6）→ 7 → 8。
首个可评审交付为阶段 1–2；用户确认版本为阶段 1–5；多 Agent 版本再增加阶段 7。
