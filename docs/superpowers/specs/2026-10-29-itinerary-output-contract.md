# 行程 Agent 输出契约（设计）

## 目标

让模型只决定已选地点的游玩日期、开始时间和安排理由。地点身份、坐标、分类、停留时长、门票、费用、酒店及交通均由服务端持有和拼装。针对日志中模型重复、错用 `activity_id` 的问题，Function Calling 参数不再包含任何地点 ID、名称或索引。

## 输入

服务端在每次调用前冻结一个有序地点列表 `ordered_places`，顺序由服务端稳定确定（例如用户选择顺序，随后稳定 ID 排序），并在本次调用及修订中保持不变。发给模型的是按此顺序排列的地点说明、类别、必去程度、已确认坐标、完整的用户攻略原文、从攻略提取的分天/先后/时间段/用餐/时长要求，以及可游玩时间；内部 ID 不出现在模型上下文。交通和酒店给模型只读时间窗口及地理位置，不让它重写原始候选。

服务端保存 `ordered_place_ids`，不发给模型。输入文本中的攻略地点关系转换为对应地点名称和列表顺序的说明；同名地点同时附已确认地址以供区分。模型的反馈使用“输入第 N 个地点”及具体冲突，而非内部 ID。模型必须以用户攻略为每日排程的首要依据：明确写了“第 2 天”“上午”“先 A 后 B”的要求优先于距离聚类或通用推荐；未指定的部分再结合通勤、节奏和营业信息安排。攻略要求与已选交通或时间窗口冲突时，输出未安排原因，由系统提示用户处理，不擅自更改原文要求。

## Function Calling 输出

只允许调用一次 `submit_itinerary_schedule`。参数仅有一个 `placements` 数组，其长度必须等于 `ordered_places` 长度；第 N 项对应输入第 N 个地点，模型不可改变对应关系。示例：

```json
{
  "placements": [
    {"day": 1, "time_of_day": "10:00", "reason": "上午参观"},
    {"day": 2, "time_of_day": "12:00", "reason": "午餐"},
    {"day": null, "time_of_day": null, "reason": "返程前时间不足，暂未安排"}
  ]
}
```

`day` 为旅行第 1..N 天的整数或 `null`；`time_of_day` 为有效的 24 小时 `HH:MM` 或 `null`。二者必须同时存在或同时为 `null`。`reason` 为简短非空解释；未安排时必须说明原因。模型不输出 `activity_id`、地点名称、坐标、`duration_minutes`、费用、交通、酒店、`unscheduled` 或 `constraint_results`。已明确的时长由服务端原始地点数据提供，原文硬约束及预算由确定性审核生成结论；模型不能自称满足。

函数 schema 使用 `additionalProperties: false`，属性均列入 `required`，允许 `day` 和 `time_of_day` 为 `null`。数组长度按本次地点数动态设置 `minItems = maxItems = len(ordered_places)`；模型服务不支持动态长度约束时，服务端仍按此长度校验。空地点列表允许空数组。

## 服务端拼装与验证

1. 校验恰好一次正确的 Function Calling、参数结构、数组长度、日期与时间范围及 `null` 配对。失败不写入行程，按现有上限有限重试。
2. 对 `zip(ordered_place_ids, placements)`：安排项从服务端原计划读取名称、分类、坐标、时长、费用及购买记录；未安排项形成 `{activity_id, reason}`。模型不能提供或覆盖这些字段。
3. 服务端加入去返交通、家与酒店锚点，用保存的 POI 坐标算通勤，再把最终每日安排逐条与用户攻略的指定日期、时间段、先后顺序、停留时长及用餐要求核对，同时检查必去和预算。审核生成真正的 `constraint_results`；不满足的硬要求阻止最终确认，并给模型有限次修订机会。
4. 修订时继续使用同一份冻结的地点顺序；如果用户期间修改了地点列表，取消本轮结果，基于新快照重新调用。并发请求通过输入摘要识别旧结果。
5. 输出长度正确但语义错位无法靠纯位置数组检测，例如模型把第 2 项的理由写给第 3 项。理由只供解释，身份绑定始终以服务端顺序为准；审核只认可日期、时间和原文约束。若需要从模型语义层严格证明逐项对应，后续可改为逐地点调用，代价是调用次数和延迟增加。

## 代码修改点

- `agent/itinerary.py`：更换输入快照、提示词、Function Calling schema 和 `_validate_proposal`；移除 `print("data:", data)`，改为在日志中记录摘要与校验错误，避免整份用户攻略写入日志。
- `agent/planning_graph.py`：在请求前保存有序 ID 列表，修订复用同一顺序；将模型的 `placements` 拼成现有 `draft_itinerary` 所需的内部 `stops/unscheduled`。
- 测试：两家同名分店、不同数量的地点、空列表、未安排点、非法日期/时间、错误 Function Calling、修订顺序稳定、模型注入额外身份字段被拒绝，以及原文硬约束由程序审核。
- 增加攻略例子：“D1 灵隐寺→永福寺；D2 上午九溪烟树，午餐知味观”，核对第一天的顺序、第二天的日期和午餐时间；不能仅因两地点更近就把第二天内容挪到第一天。若交通时间无法满足，结果必须明确列出冲突。
