# Travel Planner 项目难点与解决笔记

最后更新：2026-11-19。

整理范围：当前工作空间最近更新的 20 条历史对话，不含本次整理，更新时间为 2026-11-15～2026-11-19。相同问题已合并，以较新的修复结论为准；原对话入口见文末。

状态说明：**已修复**表示历史对话已有实施和验证记录；**部分完成**表示仍有缺口；**待验证**表示只有分析、方案或缺少真实服务验证。本次整理没有重新运行业务测试。

## 最核心的难点

把一份零散攻略变成“地点找得到、时间排得下、修改存得住”的行程。模型负责理解和建议，地图提供地点与路程，程序负责检查和保存；任何一环失败，都要说明原因并保住已有成果。

```mermaid
flowchart LR
    A[攻略或修改要求] --> B[理解需求与提取地点]
    B --> C[查询真实地点和路程]
    C --> D[排序与安排时间]
    D --> E[检查问题并让用户选择]
    E --> F[保存与展示路书]
```

## 怎样衡量改进，避免只看“测试通过”

| 看什么 | 已有证据与正确理解 |
| --- | --- |
| 地点是否排全 | 西安失败样本是 **1/13**，说明“完成状态”会掩盖遗漏；修复后仍需用同一输入复跑。[S20] |
| 发给模型的内容是否变少 | 单日审核上下文 **11,816 → 4,185 字符，减少 64.6%**；地图搜索样本 **8,707 → 1,225 字符，减少 85.9%**。这是体积变化，不能直接说速度提高同样比例。[S06] |
| 能否保住局部成果 | 一类查询失败后，其余真实候选仍可查看；缺少的组、失败原因和保存状态明确，过期结果不能复用。[S01]、[S02] |
| 用户能否真正完成操作 | 不只检查接口返回成功，还要确认选择、试算、保存、刷新后的内容和路书一致。[S04] |

S17 曾转述更早样本“已定位地点的排程覆盖率 0/32 → 32/32”。本次未直接复核该更早对话与原始运行，暂作线索，不作为最近 20 条对话重新验证出的成果。

## 仍需跟进

- **真实服务复测**：最新格式纠正、零执行拦截、并发搜索，以及真实高德、图片与数据库组合仍需针对性验证，历史离线通过不能代替线上效果。
- **既有测试失败**：S01 最后记录全量 437 项中 423 通过、13 个既有失败或报错、1 跳过；这是当时的报告，本次未重跑，也未逐项修复。
- **尚未补齐的能力**：指定日期的景点营业/预约核验、酒店实时房态和价格，仍缺可靠数据来源。[S07]
- **接入和组织缺口**：小红书主链路未验收；公开工具业务代码尚未按领域拆出；模型参数是否实际透传需单独验证。

每次项目对话结束前，若有新的问题、根因、修复办法或验证结论，更新对应条目；重复问题合并，独立问题新增。使用简短中文，写清“发生什么、为什么、怎么处理、验证到哪”。补上日期和对话或文件证据，更新顶部日期；只有方案时标为待验证，后续验证后再改状态。
